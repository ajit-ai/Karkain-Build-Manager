# Karkain Build Manager — Product Specification

**Document status:** Design COMPLETE. Research = COMPLETE. Repository creation = COMPLETE. Application implementation = NOT STARTED. Application compile/execute verification = NOT STARTED (toolchain path itself VERIFIED on Karkain v1.2.0).


## A. Product definition

Karkain Build Manager is a CLI/TUI service that orchestrates builds of Karkain workspaces: it resolves a dependency graph, decides what to rebuild using content hashes, schedules toolchain steps, caches artifacts and records diagnostics and measurements — but it does not compile source itself. **Problem.** [VF] Gradle provides incremental builds, caching and dependency management via Groovy/Kotlin DSLs on a JVM; Bazel provides a rigorous action graph, hermetic sandboxing and remote execution via Starlark; Ninja is a minimal fast graph usually generated by other tools. [RI] Each brings its own runtime or DSL and none is co-designed with a compiler's own workspace graph and diagnostics contract. **Vision.** A build manager native to the Karkain toolchain: consume `workspace graph` directly, use `karkain-diagnostics-v1` codes and `bench`/`prof` as artifacts, verify packages with `pkg audit/verify` and `crypto`, and ship as a small C-free binary with no extra runtime. **Intended users/segments.** Karkain developers with multi-package workspaces, CI/agent integrators, supply-chain-conscious teams on ~4 GB RAM. **Usage scenarios.** (1) Incremental rebuild of a workspace; (2) inspect the dependency graph; (3) verify dependency integrity; (4) consume build artifacts/diagnostics in CI. **Market positioning.** A single-toolchain, zero-extra-runtime orchestrator, not a Bazel-style remote-execution platform. **Primary value proposition.** Deterministic, scriptable incremental builds with no new language/runtime and build metadata flowing into project/test tooling. **Explicit non-goals/boundaries.** Not the compiler; not a general build DSL for other languages; not an IDE/editor/project tracker; no GUI in v1.2.0 (BLOCKED); no remote execution, hermetic sandbox or distributed cache claims; no pricing/adoption/benchmark claims. [VF/RI]

## B. Functional architecture

| Module | Responsibility |
|---|---|
| graph-svc | Parse `workspace graph` into a target/dependency model; detect cycles |
| change-detect | Hash inputs with `crypto` sha256; decide dirty targets |
| scheduler | Run independent build steps cooperatively via `async` |
| cache-mgr | Store/retrieve artifacts keyed by content hash |
| artifact-svc | Write build manifests, diagnostics and `bench`/`prof` artifacts |
| verify-svc | Run `pkg audit`/`verify` and hash checks |
| cli-api | `build`, `rebuild`, `graph`, `clean`, `verify` commands + JSON |
| tui-dash | Terminal build dashboard and graph view |
| config | Cache location and policy via `config` |
| logging | Structured build log with exit codes |

**Core workflows.** Parse graph → hash inputs → select dirty targets → schedule steps → cache artifacts → emit JSON manifest. **Admin workflows.** Configure cache location, clean cache, set verification policy. **Error/recovery workflows.** On a failed step, capture its `E-K-*`/`W-K-*` diagnostics and abort dependents; on cache corruption, evict the entry and rebuild. **Roles & permissions.** Single local user; no multi-tenant auth. **Configuration/customization.** Cache path and parallel policy via `config`. **Import/export.** Restricted JSON build manifest (PARTIAL `json_get_field`). **Integration requirements.** `workspace`, `pkg`, `crypto`, `bench`, `prof`, `test`, `io`, `async`. [VF/RI/PROPOSAL]

## C. Competitor analysis

Researched benchmarks: **Gradle**, **Bazel**, plus **Ninja**. [VF] Gradle (Develocity) is the open-source JVM/Android/Kotlin build system with incremental builds, caching, a daemon, parallel execution and Groovy/Kotlin DSLs; Bazel is a multi-language, multi-platform build/test tool with a Starlark action graph, hermetic sandboxing, remote caching/execution and query; Ninja is a minimal fast edge-graph build tool usually generated by CMake/Meson. All three are Apache-2.0 (verified from official repositories). Feature comparison matrix (Karkain = **proposed**):

| Capability | Karkain (proposed) | Gradle | Bazel | Ninja |
|---|---|---|---|---|
| Dependency graph | `workspace graph` (PRESENT) | Task graph, deps | Action graph, query | Minimal edge graph |
| Incremental/cache | Proposed via content hashes | Incremental + cache | Caching + remote exec | Fast incremental only |
| Hermetic sandboxing | UNKNOWN — not verified | Limited/native deps | Sandboxed by design | None |
| Supply-chain verify | `pkg audit/verify`, `crypto` (PRESENT) | Dependency verification | Reproducibility | None |
| Extension language | Karkain/workspace | Groovy/Kotlin DSL | Starlark | Generated files |
| Reporting/Build Scan | JSON + TUI proposed | Build Scans/Develocity | Partners/UI | External tooling |
| License | Karkain toolchain (proposed) | Apache-2.0 | Apache-2.0 | Apache-2.0 |
| Startup footprint | C-free native binary (VERIFIED on Windows) | JVM/daemon | Single binary | Single binary |

**Platform/deployment.** Gradle runs on JVM platforms, self-provisions via wrapper; Bazel via Bazelisk on Linux/macOS/Windows; Ninja is a small standalone binary; Karkain is a C-free native binary (Windows VERIFIED). **Licensing comparison.** Gradle/Bazel/Ninja Apache-2.0 status is VERIFIED; Develocity commercial pricing is **UNKNOWN — not verified**; Karkain toolchain licensing UNKNOWN — not verified. No prices invented. **Strengths/limitations.** [VF+RI] Gradle: ergonomics/dependency breadth but JVM/daemon memory and DSL complexity; Bazel: correctness/hermeticity/scale but steep learning curve and BUILD upkeep; Ninja: speed/simplicity but no dependency resolution; Karkain: coherent single toolchain and tiny footprint but no remote-execution ecosystem and PRESENT-not-executed capabilities. **Market gaps.** [RI] A build manager co-designed with its language toolchain, deterministic diagnostics/exit codes, minimal footprint and build metadata flowing into project/test tooling. **Differentiation.** [RI/PROPOSAL] Use `workspace graph` as the graph, `karkain-diagnostics-v1` + `bench`/`prof` as artifacts, `pkg audit/verify` + `crypto` for supply chain; not Bazel's remote-execution ecosystem (out of reach without gRPC/TLS). **Features deliberately not copied:** Starlark/Groovy DSLs, remote execution/cache protocols, hermetic sandbox claims, build-scan SaaS. Consistent with `docs/competitor-analysis/COMPETITORS.md`. [VF/RI/UA]

## D. Technical architecture

**Application architecture.** CLI/TUI frontends over a build orchestration core with toolchain adapters. **Component boundaries.** Each module is an independent Karkain component exchanging JSON contracts. **Process/service boundaries.** One local orchestrator process; build steps invoke the Karkain toolchain; optional local stdio service for CI/agents. **UI architecture.** CLI/TUI/service-first is explicit: Karkain v1.2.0 has no native GUI toolkit (BLOCKED), so no windows, controls or event loop; any GUI is a **planned layer contingent on ecosystem capability**, supplied by an external host, never a v1.2.0 claim. **Domain model.** BuildTarget, DependencyEdge, ContentHash, Artifact, BuildManifest, Diagnostic, StepResult. **Data storage strategy.** File-based artifact/cache directory; no database needed. **API/interface architecture.** Stdio JSON commands (`build`, `graph`, `verify`, `clean`) + JSON artifact files. **Event/message architecture.** `async` channels/pool for cooperative step scheduling (not preemptive threads). **Logging/diagnostics/observability.** Structured JSON build log with step durations and exit codes. **Configuration management.** Versioned `config` file. **Plugin/extension architecture.** None in MVP; no GUI plugin API; no external DSL. [VF/RI]

## E. Data design

**Main entities.** BuildTarget (id, package, command), DependencyEdge (from, to), ContentHash (path, sha256), Artifact (target_id, path, hash), BuildManifest (workspace, targets, diagnostics, timestamp), StepResult (target, exit_code, output). **Relationships.** Target N—N Target via DependencyEdge; Target 1—N Artifact; BuildManifest N—1 per build run. **Ownership.** Local user owns the workspace and cache. **Validation.** Cycles in DependencyEdge rejected; hashes compared with `crypto`; manifest fields validated against a restricted shape. **Lifecycle.** target dirty→building→cached/failed; manifest written on completion. **Persistence.** Artifact/cache files and JSON manifests; atomic write not verified (PARTIAL OS atomic-write), so writes are validated after writing. **Transactions.** Not applicable (no DB); step failures abort dependents. **Backup/restore.** Copy the cache/artifact directory. **Migration.** Manifest version field. **Import/export.** Restricted JSON manifest (PARTIAL `json_get_field`). **Audit history.** Append-only JSON build log. **Storage decision.** File-based cache + append-only log is appropriate: embedded `db2` is unnecessary, and content hashing avoids PARTIAL filesystem metadata (mtime/permissions). [VF/RI]

## G. Non-functional requirements

- **Performance.** Workload: incremental rebuild of a 100-target workspace with 1 changed file; method: `bench` timing; target: rebuild only the affected subgraph in < 5 s on ~4 GB RAM (measurement plan, not achieved).
- **Memory.** Workload: graph of 100 targets loaded; method: OS task-manager sample; target: resident set < 250 MB.
- **CPU.** Workload: hashing 10,000 source files; method: `prof`; target: < 20% sustained.
- **Scalability.** Workload: 1→1,000 targets; method: scripted generation; target: graph resolution linear.
- **Reliability.** Workload: interrupted build; method: fault injection; target: cache stays consistent, retry rebuilds only dirty targets.
- **Security.** Workload: tampered dependency; method: flip a hash; target: `pkg verify` + `crypto` detect mismatch.
- **Privacy.** All build data local; no telemetry, no sign-in, no remote cache.
- **Portability.** Windows VERIFIED; Linux/macOS NOT VERIFIED.
- **Maintainability.** Each module documented with a JSON contract.
- **Accessibility.** Fully keyboard-operable TUI and complete CLI.
- **Observability.** Every step logged with exit code and duration.
- **Recovery.** Evict corrupt cache entry and rebuild. [RI]

## I. Testing strategy

**Unit.** Graph parsing, cycle detection and hash comparison; criterion: all functions covered. **Integration.** `workspace graph` → model and cache read/write; criterion: correct dirty selection. **E2E.** Build → change one file → rebuild; criterion: only affected targets rebuilt, manifest matches. **Platform-specific.** Windows native binary; criterion: compile + run smoke test. **Security.** Tampered hash/dependency; criterion: mismatch detected by `verify`. **Performance.** 100-target incremental build; criterion: meets G target. **Regression.** Prior-bug corpus; criterion: zero regressions. **Compatibility.** v1.2.0 toolchain contract; criterion: workspace graph parses, diagnostics match schema 1. **Actual-compiled-executable.** Build with `KARKAIN_ENGINE=go` + native-x86_64-windows, run `.exe`; criterion: expected stdout/manifest. **Failure/recovery.** Inject failed step; criterion: dependents aborted and cache consistent. **All tests PLANNED; none run yet for this application.** [VF/RI]
